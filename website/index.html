01 — The problem

Generic load balancers cannot see a GPU.

Serving LLMs across your own fleet creates failure modes that nginx never had to name. Marbor exists because those failure modes are expensive.

01.01

VRAM thrashing

Without a scheduler, models are loaded ad-hoc. When memory fills, the runtime evicts a resident model to make room. The next request pays a 15–45 second cold start. Hardware wears. SLAs die.

01.02

Queue hotspots

A TCP balancer treats a deep reasoning call the same as a short completion. Work piles onto a busy node while neighbouring GPUs sit idle, because the balancer cannot read queue depth or residency.

01.03

Silent cloud spend

When local capacity is exceeded, traffic either 502s or overflows to OpenAI and Anthropic with no meter. The bill arrives at month-end. Nobody can say which key spent what.

Placement

Marbor polls node state and VRAM layouts every two seconds. It schedules on live model residency, spreads queue depth across the fleet, and overflows to the cloud only when local capacity is genuinely saturated. Every token is counted.

02 — Capabilities

A control plane, not a reverse proxy.

Point every application at one URL. Marbor handles warm-state routing, failover, authentication, rate limits, and cost analytics across the runtimes you already run.

02.01 Routing

Warm-state VRAM scheduling

Requests go to the node where the target model is already resident. Cold work is placed on the GPU with the most free VRAM. Session affinity via X-Session-ID keeps the KV-cache hot across turns.

02.02 Failover

Local first, cloud only when full

Unhealthy nodes are skipped. Saturated clusters can overflow to OpenAI or Anthropic — off by default, metered when enabled. Traffic returns to local hardware the moment queue depth clears. Format translation is invisible to the client.

02.03 Cost

Token accounting, not estimates

Every locally served token is valued against your cloud reference rate. Per-key monthly spend, daily and monthly quotas, and a savings figure computed from parsed token counts — eval_count or usage.total_tokens. Missing data shows as “—”, never a fabricated number.

02.04 Gateway

OpenAI-compatible, with teeth

Bearer tokens, per-key model allow-lists, rate limits, and quotas on /v1/chat/completions. Continue, LibreChat, Open WebUI, and the OpenAI SDK work by changing a base URL.

02.05 Fleet

Five runtimes, one endpoint

Ollama, vLLM, TGI, llama.cpp, and MLX. Declare runtime per node. Protocol translation is automatic. Mix hardware and mix servers behind a single address.

02.06 Operations

A binary, an optional agent, a dashboard

The control plane is one static Go file. The optional marbor agent on each GPU host adds live telemetry, model pulls, and runtime control. Twenty Prometheus metrics and an embedded admin UI ship in the same binary. No sidecar zoo required to see the cluster.

04 — Install

A binary. Then a URL.

The control plane is one static Go file. The marbor agent is optional, and only for hosts that need richer telemetry or node-side operations.

01

Install the binary

A release for your platform, or build from source. One file. No runtime dependencies.

Install only

curl -fsSL raw.githubusercontent.com/Anirudhx7/marbor/main/install.sh | sh

Install, scan the local network, run in the background

curl -fsSL raw.githubusercontent.com/Anirudhx7/marbor/main/install.sh | START=1 sh
02

Point it at your nodes

Add nodes from the dashboard, or seed them at install. No config file. Set runtime per node.

# seed at install time
marbor --seed-node "name=ollama-gpu,url=http://gpu-01:11434,runtime=ollama" \
       --seed-node "name=vllm-gpu,url=http://10.0.1.20:8000,runtime=vllm"
03

Send traffic to one URL

Repoint applications at Marbor. Same OpenAI-compatible surface. Routing happens behind it.

# your app, otherwise unchanged
base_url = "http://marbor:11434/v1"

06 — Questions

In short.

What is Marbor?

A single-binary control plane for self-hosted AI inference. It routes each request to the GPU node that already holds the model warm in VRAM across Ollama, vLLM, TGI, llama.cpp, and MLX, and exposes one OpenAI-compatible endpoint so your own hardware becomes a high-availability alternative to cloud LLM APIs.

How is it different from nginx or HAProxy?

Those balance TCP connections. They have no view of which GPU holds a model, so they route blindly and cause repeated cold starts. Marbor reads live residency and VRAM on every node and schedules to a warm GPU.

Does it work with vLLM, TGI, llama.cpp, and MLX — or only Ollama?

All five. Marbor is runtime-agnostic. One OpenAI-compatible endpoint, protocol translation included, so you can mix runtimes behind a single URL.

Can it replace cloud LLM APIs?

That is the point. Requests are served from your GPUs first. Overflow to OpenAI or Anthropic happens only when local capacity is saturated, and every cloud token is metered.

How does failover work?

A down node is marked unhealthy and skipped. If the whole local cluster is saturated or down, Marbor can fail over to a configured cloud provider. The routing path is stateless, so you can run multiple instances behind an L4 load balancer.

Can I put auth and rate limits in front of my models?

Yes. Bearer-token authentication, per-key model allow-lists, and per-key rate limits with daily and monthly quotas — without changing application code.
